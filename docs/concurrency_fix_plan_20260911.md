# План виправлення керування операціями

Обсяг: перші три погоджені пункти аудиту. Без tenant-моделі, Telegram і серверного розгортання.

1. Signal-only cancel для всіх сценаріїв, один власник драйвера, переривне ручне очікування; гарантована фіналізація runner, включно зі скасованими queued задачами.
2. Спільне локальне резервування фактичного AdsPower profile ID на час сценарію/iCloud і перевірка manual start/stop. Зайнятий профіль відхиляє іншу операцію зі зрозумілим повідомленням; чинна робота не переривається.
3. Версія запису задачі, атомарні зміни під транзакцією, прямий пошук ID; окремий маркер зовнішньої дії, міграція старого resume_data. Незмінний snapshot акаунта та комплекту РК, атомарний запис журналу.

Регресії: pause/stop A не впливає на B; два workers і один профіль; cancel до старту; execute/cleanup exception; callback exception; shutdown із queued/running; manual assist після впізнаного стану; stale task write; progress після completion; попередній unknown; зміна оригіналу документа після підготовки.

Браузери та реальні подачі під час перевірки не запускаються. Робоча БД не мігрується інструментами розробки: перевірка міграцій відбувається на тимчасових БД, застосунок застосує міграцію при наступному запуску.

## Реалізовано

- BaseScenario: копія Account, спільний власник фактичного профілю, керування командами навіть для перевизначеного старту браузера. Screenshot cancel більше не викликає WebDriver у Tk-потоці. Cleanup не замінює результат; при збереженні AdsPower-браузера зупиняється лише його Chromedriver service.
- ScenarioRunner: фіналізація винятків execute, queued cancellation і помилок callback; заборона submit після shutdown. Статус running встановлюється при фактичному старті worker.
- UI: облік завершених операцій змінюється у Tk-потоці; ручне очікування після впізнавання сторінки реагує на cancel; CAPTCHA прив’язані до акаунта. Повтор створює нове завдання, залишаючи старий результат незмінним. Tk більше не аналізує драйвер після звільнення профілю worker.
- ProfileAccess: спільне резервування сценаріїв, iCloud HME, manual start/stop. Screenshot використовує main_profile_id, а не AdsPower-профіль РК-акаунта. HTTP Session AdsPower окрема для кожного потоку.
- TaskRepositoryMixin: атомарні зміни BEGIN IMMEDIATE, version/CAS для повних записів, прямий пошук ID. Термінальний результат захищений від запізнілого progress/pause/completion. external_action_pending — окрема колонка з міграцією старих записів. Непідтверджений результат зберігається як outcome_unknown.
- OperationEventService: записи у SQLite переживають перезапуск і закриття UI. Очищення UI не видаляє журнал.
- Комплект РК копіюється до My_Accounts/.operation_inputs перед передачею в чергу; назви файлів збережені, manifest містить SHA-256. Дані вибраних депозитів також фіксуються до черги. Налаштування та журнал РК записуються атомарною заміною через унікальний тимчасовий файл.

## Перевірка

21 нова регресійна перевірка у tests/test_concurrency.py. Повний unittest discover: 88 тестів, 56 успішних, 32 браузерних пропущено (потрібен ізольований Chrome). Перевірено компіляцію модулів і git diff --check для змінених відстежуваних файлів. Монітор ресурсів BaseScenario замінено mock; тести БД працюють лише з тимчасовими файлами. Реальні браузери, акаунти та подачі не запускалися.

## Межі цієї реалізації

Блокування профілів діє в одному процесі застосунку; інша копія програми або зовнішній AdsPower-клієнт його не використовує. Серверний міжпроцесний lock належить до наступного етапу. Cancel кооперативний: уже розпочатий HTTP/WebDriver-виклик завершується або досягає власного timeout, після чого worker обробляє сигнал. Це не примусове вбивство потоку.

Копії документів і журнал зберігаються для перевірки та відновлення; автоматичне видалення за строком зберігання не вводилося. Серверна ізоляція користувачів, Telegram, загальний AdsPower rate limiter та перебудова решти daemon jobs у цій зміні не реалізовувалися. Робоча БД мігруватиме при наступному запуску застосунку.

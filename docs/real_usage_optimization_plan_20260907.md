## Докази та пріоритети

### P0: введення Notes і передумови Create API

`create_mexc_api._fill_note` викликає `clear_and_type`, потім без перевірки пише
`api_note_filled`. Спільний helper застосовує JS fallback лише при винятку:
успішний send_keys з порожнім/скинутим значенням не викликає fallback.
У probe 13.08 (`8617129d2262`) та 02.09 (`2260dbf64c34`) memo має valueLength=0,
security inputs відсутні, але підсумкова помилка стосується email input/Get Code.
Це узгоджується зі спостереженням користувача; самі логи не доводять втрату фокуса
як єдину причину. У двох успішних API-запусках 06.09 Notes був заповнений.

План: окремий перевірюваний helper введення з повторним пошуком DOM-елемента,
правильним setter для input/textarea, input/change та перевіркою після blur і
наступного рендера. Не змінювати React internals. Максимум дві спроби; після
невдачі точне повідомлення про Notes. Перед Create повторно перевірити memo,
permissions, agreement, відсутність помилок. Після Create чекати конкретно
security modal, результат створення або помилку форми; не шукати Get Code на
порожній основній формі. Успішні події писати тільки після перевірки результату.

### P0: реєстрація — переходи та підтвердження результату

У телеметрії: 8 збоїв Continue на register_email, ще по одному на unknown і
browser_closed; 6 таймаутів кінцевої перевірки 30 с; 3 таймаути пошти 180 с;
3 транспортні таймаути WebDriver по 120 с. 03.09 є серія повторних невдалих
запусків на одному акаунті — повтор з початку не усуває причину.

План: до Continue перевірити email/referral/локальні помилки; після кліку одним
очікуванням відстежувати code/password/success/CAPTCHA/error/browser_closed.
Закриття вкладки одразу класифікувати як зупинку. Після фінального Submit
розрізняти підтверджений успіх, явну відмову та невідомий результат. Не повторювати
створення акаунта автоматично після втрати відповіді. Збереження пароля виконати
на підтвердженому успіху; невідомий результат запропонувати перевірити через login.
Referral fallback обмежити невеликою кількістю перевірених спроб; оптимізувати
після основних переходів — у свіжих логах це не найбільша виміряна затримка.

### P0: правильне управління задачами та Tk

02.09 API-задача `db3e53ebfe84` впала з `main thread is not in main loop`.
Без повного stacktrace точний callback не встановлений. У коді багато викликів
Tk after з worker-потоків. BaseScenario.cancel викликає driver.quit і stop_browser
синхронно; переносити такий виклик безпосередньо на нову UI-кнопку не можна.
TaskService зараз зараховує скасування до failed; довільної робочої паузи немає.

План: потокобезпечна черга повідомлень, яку Tk читає своїм after у головному
потоці; жодних Tk-операцій з worker. Окремий OperationController з cancel/pause
сигналами, snapshot задачі й блокуванням переходів. Кнопки лише встановлюють
сигнал; cleanup виконується поза UI. WebDriver має одного власника, паралельний
quit не повинен змагатися зі звичайними командами. Обмежити транспортні таймаути
і передбачити окрему ескалацію зупинки завислого драйвера через AdsPower.

### P1: API/2FA — прив'язка до поточної форми

2FA `6d6523f71127` від 29.08: emailCode містить 6 символів і Submit є в probe,
але сценарій повідомив, що кнопки немає. Наявність DOM-кнопки ще не доводить її
готовність у момент невдалого кліку. Поточний код уже містить inline fallback —
потрібна перевірка обох варіантів, а не дублювання workaround.
API: дві явні невдачі security verification, по одній помилці email input і
Get Code, один manual-assist timeout 10 хвилин.

План: єдина модель email-only, TOTP-only, combined, inline/modal, completed.
Кнопку шукати в контейнері активного поля; після re-render знаходити заново.
Перевіряти введення email/TOTP; TOTP генерувати безпосередньо перед відправленням.
Повторювати лише явно відхилений/прострочений код з лімітом. Зникнення modal
саме по собі не є успіхом. Зберігати 2FA secret як pending до підтвердження
прив'язки; збережений секрет не прирівнювати до активної 2FA. API-ключі надійно
зберігати до закриття одноразового вікна, не створювати дубль після невідомого
результату. Обробити KYC/login redirect окремим повідомленням.

### P1: прибрати зайві очікування

06.09 успішна 2FA-задача `81002f0454ae`: три перевірки відсутньої CAPTCHA
9,7 + 10,4 + 8,4 ≈ 28,5 с. API `6b508cde01e9`: перевірки відсутньої CAPTCHA
19,4 і 11,0 с; отримання листа окремо зайняло 17,3 с. Реєстрації 05 і 07.09:
приблизно 11 с перевірки відсутньої CAPTCHA після signup.

План: поширити підхід швидкої перевірки RK на інші сценарії, але постійно
перевіряти пізню CAPTCHA в очікуванні наступного стану. Замість послідовних
таймаутів на кожен selector — один DOM snapshot і загальний deadline етапу.
Використовувати monotonic, переривні очікування, закріплену вкладку сценарію.
Прибирати fixed sleep лише там, де його замінює перевірка стану.

Телеметрія займає 94,1 МБ; 692 з 5 028 вимірювань мали RAM >=90%, максимум
99,2%. Це фактор ризику, а не доведена причина конкретного збою. Додати ротацію,
компактні записи, окремий детальний snapshot на збій. Асинхронна черга вже є в
поточному коді. Ліміт одночасних профілів залишити явним налаштуванням; не
закривати чужі профілі автоматично.

## Журнал та індикатор акаунта

Над історією закріпити панель активних операцій. Для кожної: акаунт, сценарій,
етап, стан, тривалість етапу, останній прогрес і причина очікування. Окремо
оновлювати heartbeat worker та фактичний прогрес — анімація не доводить роботу.
Кнопки: «Пауза»/«Продовжити» і «Припинити операцію». Вони прив'язані до task_id;
при кількох операціях кожна має власний рядок. Очищення журналу очищає історію
на екрані, не прибирає активну операцію і не скасовує її.

Стани: queued, running, waiting_email, waiting_captcha, waiting_network,
waiting_user, pause_requested, paused, cancelling, cancelled, completed,
failed, outcome_unknown. У БД можна зберігати базовий status і окрему wait_reason,
щоб не розросталися несумісні enum. Усі UI-компоненти читають одне джерело стану.

На вкладці акаунта: невеликий індикатор роботи; символ паузи для paused;
жовтий знак очікування з підказкою причини. Колір дублювати символом/tooltip.
Індикатор прибирається на кінцевому стані; помилка залишається в журналі.
Оновлювати лише потрібний віджет, не перебудовувати вкладку щосекунди.

Рекомендована семантика для погодження перед реалізацією:

- Пауза на найближчій безпечній межі; до цього «Призупиняю…». Уже надісланий
  серверу запит не відкликається. Під час паузи нові кліки/запити не виконуються.
- Локальний таймер очікування можна призупинити; строк життя email/TOTP і
  мережевого запиту продовжується. Після resume перечитати сторінку, оновити
  прострочені коди, врахувати ручні дії, не повторювати фінальний Submit.
- Рекомендація: Stop залишає браузер відкритим для огляду. Це зміна поточної
  поведінки cancel, яка закриває профіль, тому потребує вибору користувача.
- Якщо зупинка/краш стався після Submit, показати outcome_unknown до перевірки.
  Після перезапуску програми старі running не відображати як реально активні.

## Розбиття реалізації і перевірка

1. Перевірюване введення Notes + контроль переходу Create; DOM-фікстури фону,
   blur, re-render, stale element, порожнього memo і видимої помилки.
2. OperationController, UI-черга, коректні cancelled/unknown, активний журнал,
   кнопки та значок. Тести pause/resume/stop у пошті, CAPTCHA, мережі, у черзі,
   після Submit, під час закриття застосунку та з двома акаунтами одночасно.
3. Переходи реєстрації, підтвердження результату й bounded recovery.
4. Уніфікація станів security API/2FA, перевірка збереження ключів/секретів.
5. Спільні очікування, закріплення вкладки, ротація журналів; порівняння
   часу етапів до/після за окремими сценаріями, без часу ручної CAPTCHA.
6. Контрольовані реальні прогони у foreground, після Alt+Tab і при зміні вкладки.
   Нову реєстрацію/2FA/API створювати лише в погодженому тестовому обсязі.

Критерії: жодної події filled без перевіреного значення; відсутня CAPTCHA не
створює окремого восьмисекундного очікування; UI реагує на кнопки одразу та
чесно показує pending pause/cancel; у звичайних циклах сигнал обробляється
до 1 с, для WebDriver вказаний окремий deadline; немає дублювання Submit;
завершення/помилка/зупинка прибирають активний індикатор; секрети не потрапляють
у журнал; відсутні worker-виклики Tk. Таймаути не підміняють перевірку результату.

## Реалізація та перевірка — 08.09.2026

Реалізовано у коді:

- `verified_input.py`: контроль значення після вводу, blur і повторного рендера,
  повторний пошук input за id, fallback з коректним setter для textarea/input.
- API: повторна перевірка Notes, permissions та agreement до Create; очікування
  security-форми/помилки замість сліпого пошуку Get Code; збереження і читання
  API-ключів назад до закриття одноразового вікна; один повтор явно відхиленого
  email-коду, обмежені повтори TOTP, перевірка реального результату.
- `security_submit.py`: Submit шукається біля потрібного email/TOTP-поля в його
  формі; підтримано inline та modal, combined-етап 2FA.
- Швидка перевірка CAPTCHA без окремого восьмисекундного очікування; пізню
  CAPTCHA перевіряють очікування переходів. Підтвердження 2FA більше не
  ґрунтується лише на зміні URL чи довільному слові success у тексті.
- `operation_control.py`: кооперативні pause/resume/stop; Stop залишає профіль
  відкритим. Короткий етап генерації TOTP і Submit відкладає паузу до безпечної
  межі, але зберігає можливість скасування.
- `thread_dispatch.py`: worker передає UI-виклики через чергу; Tk планує їх у
  власному потоці. Питання мережі/email не блокують доступ до кнопок операції.
- Активна панель над історією журналу, кнопки паузи/продовження/припинення,
  час етапу, стан очікування й давність відповіді worker; символ роботи/паузи/
  очікування на вкладці акаунта. Очищення історії не прибирає панель операції.
- Окремі cancelled/outcome_unknown, збереження маркера зовнішньої відправки,
  відновлення перерваних задач як невизначених та перевірка перед новим запуском.
  Ранній 2FA secret позначається pending до підтвердження прив'язки.
- Закріплення вкладки через CDP; транспортний timeout 35 с, page-load 30 с,
  script 15 с; ротація resource_usage.jsonl при 10 МБ з трьома архівами.

подовжується. Готовий EXE не перебудовувався; потрібна нова збірка main.spec.

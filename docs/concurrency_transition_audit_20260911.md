# Аудит багатопоточності перед серверним переходом

Перевірено 11.09.2026: поточні реалізації runner, базового сценарію, сценарію скриншотів депозитів, керування операціями, UI dispatch, діалогів, сервісів задач/подій, сховищ і AdsPower-клієнта. Це цільовий аудит коду з ізольованими перевірками, не навантажувальний прогін живих акаунтів. Код застосунку не змінено.

Висновок: окремі сценарії мають власні потоки й сигнали pause/cancel, проте повної ізоляції операцій немає. Спільні профілі, стан задач, вікна допомоги й записи файлів можуть конфліктувати. Серверний багатокористувацький запуск потребує виправлень до підключення Telegram.

## Як працює виконання

| Частина | Потік / спосіб виконання | Оцінка |
|---|---|---|
| Tk UI | Головний потік | Правильний власник віджетів |
| Сценарії | `ScenarioRunner`, типово 2 worker-потоки | Окремі об’єкти сценаріїв, але спільні ресурси |
| Pause/cancel | Власний `OperationControl` для кожного сценарію | Базовий механізм ізольований |
| Worker → UI | `ThreadDispatchMixin`, черга викликів | Коректна основа, не захищає довільні інші спільні об’єкти |
| Sync, створення профілю, пошук депозитів, відкриття профілю | Додаткові daemon threads у App | Не підпорядковані загальному ліміту runner |
| Монітор ресурсів | Окремий worker, bounded queue, lock | Не отримує WebDriver для паралельних команд |
| SQLite | Окреме з’єднання на метод | Не робить read-modify-write атомарним |
| Події | Спільний список у пам’яті, listeners викликаються синхронно | Немає єдиного власника чи захисту операцій зі списком |

Потоки не «скасовують один одного» автоматично. Конфлікт виникає, коли два потоки керують одним браузером, змінюють один запис або використовують один UI-контекст. Також дві задачі, що чекають CAPTCHA, займають обидва workers: третя чекає звільнення, хоча ПК може мати вільний CPU.

## P0: виправити до паралельного серверного запуску

### 1. Скасування скриншотів порушує правило одного власника WebDriver

Місця: `automation/scenarios/mexc_deposit_screenshot.py:51`, `ui/active_operation.py:39`, `ui/app.py:2655`.

Сценарій перевизначає `cancel()` і синхронно викликає `driver.quit()` та `adspower.stop_browser(main_profile_id)`. UI-кнопка прямо викликає цей метод. Отже, поки worker читає сторінку, потік UI може закривати його driver, зависнути на закритті та зупинити спільний основний профіль.

Підтверджено fake-driver перевіркою: обидва виклики виконано на потоці, що викликав cancel. Живий браузер не використовувався.

Виправлення: усі сценарії використовують signal-only cancel; cleanup виконує власник драйвера. `_start_browser()` скриншотів також обходить базову обгортку `controlled_execute`, тому єдину політику команд і pause слід застосувати до всіх способів підключення драйвера. Перевіряти не лише BaseScenario, а всі його перевизначення.

### 2. Відсутнє резервування фактичного профілю

Місця: `ui/app.py:1100`, `automation/scenarios/mexc_deposit_screenshot.py:40`, `services/profile_creation_service.py:41`.

`_running_accounts` захищає за email цільового акаунта. Скриншоти різних акаунтів відкривають один `main_profile_id`. Створення iCloud-масок також використовує налаштований основний профіль через окремий потік. Ці шляхи не мають спільного резервування. Два драйвери до одного браузерного профілю не гарантують незалежних вкладок, навігації й закриття.

Це підтверджена відсутність захисту в перевірених шляхах; реальне одночасне псування форми не відтворювалося.

Виправлення: один диспетчер резервує `(AdsPower-контекст, profile_id)` перед будь-яким запуском. Через нього проходять РК, скриншоти, iCloud, ручні open/close. На сервері ресурсний ключ має враховувати контекст AdsPower, а авторизація — власника. Блокування тільки в процесі недостатнє для кількох виконавців.

### 3. Застарілий запис задачі може стерти нові поля

Місця: `services/task_service.py:41`, `services/task_service.py:104`, `storage/database.py:542`.

Методи читають об’єкт задачі, змінюють поле і записують усі поля назад. Окремі SQLite-з’єднання не захищають логічну послідовність між читанням і записом.

Перевірка на тимчасовій БД: прочитано старий об’єкт → записано `external_action_pending=true` → старим об’єктом оновлено progress. Результат: `resume_data` став порожнім. Це детермінована імітація можливого чергування записів, а не твердження, що два поточні progress callbacks уже змагаються на кожній задачі. Для майбутніх команд бота/worker такий шлях особливо важливий.

Виправлення: точкові UPDATE, дозволені переходи станів, version/CAS або атомарна транзакція для складного переходу. Маркер зовнішньої дії не змішувати з довільними даними resume. Аналогічно перевірити повний запис Account: UI-autosave може працювати зі старим об’єктом після збереження нових API-даних worker.

### 4. Runner не гарантує завершення обліку при винятку

Місце: `automation/runner.py:30`.

Якщо `scenario.execute()` виходить винятком, `_futures` не очищається, результат не записується й callback не викликається. Базовий execute ловить багато помилок, але його `finally` теж виконує cleanup, який може кинути виняток. Runner не повинен залежати від безпомилковості всіх сценаріїв.

Підтверджено fake-scenario: Future завершився винятком, але `is_running=True`, callback не викликано, результат відсутній.

Виправлення: гарантована фіналізація runner з обробкою винятку виконання/cleanup, звільненням резервування й збереженням кінцевого стану. Зберігати unknown при невизначеному зовнішньому ефекті. Скасовані до старту Future також повинні отримати кінцевий стан. Зараз App позначає задачу running ще до фактичного початку worker; потрібне розрізнення queued/running.

## P1: керування, завершення та спільні дані

### 5. Manual assist може не реагувати на Stop до дедлайну

Місце: `ui/app.py:2055`.

Коли впізнано дозволений екран, внутрішній цикл чекає тільки `action_event` або дедлайн до 600 секунд. Там немає перевірки cancel чи закриття застосунку. Stop встановлює інший Event, тому сам по собі не пробуджує цей цикл. Зовнішній цикл перевіряє cancel, внутрішній — ні.

Виправлення: спільний переривний механізм очікування, перевірка cancel/shutdown у кожній гілці. Перед Continue перечитувати стан; не покладатися на snapshot перед довгим очікуванням. На shutdown завершувати всі запити взаємодії.

### 6. CAPTCHA-вікно спільне для всіх задач

Місця: `ui/app.py:1894`, callbacks завершення сценаріїв.

`_captcha_modal` один на App. Нова CAPTCHA знищує попереднє вікно; завершення іншого сценарію також може його закрити. Це не обов’язково зупиняє worker, але плутає ручну допомогу при паралельній роботі.

Виправлення: interaction ID + task ID, окремий стан для кожної задачі. Відповідь, Continue і Cancel перевіряють саме цей запит. `ask_operation` зараз шукає сценарій за email — для серверного керування потрібен task ID.

### 7. Журнал подій не є довговічним і не синхронізований

Місце: `services/operation_event_service.py:22`.

Попри переданий db, фактичний `emit()` пише у `_events` у пам’яті. `clear_account` і prune перебудовують список, поки workers можуть додавати події. Немає lock чи одного потоку-власника. Повільний listener виконується в потоці сценарію і затримує його.

Виправлення: запис подій у сховище, впорядкована доставка через чергу, окремий notification outbox для Telegram. Очищення UI не повинно знищувати надійний журнал подач. Ізольованого відтворення втрати події в цьому аудиті не проводили.

### 8. Файли, налаштування й змінні акаунта

Місця: `storage/settings.py:24`, `storage/file_manager.py:24`, `services/account_service.py:64`.

JSON та info.txt записуються напряму без спільного протоколу. Зміна статусу/імені переміщує папку, а сценарій може мати старий шлях до документів. Поточний об’єкт Account також передається сценарію без незмінного snapshot.

Виправлення: незмінний комплект запуску; стабільні account/document IDs; атомарне збереження файлів; узгодження переміщення/видалення з активною операцією. Для сервера — дані й секрети окремого користувача, а не глобальні налаштування всіх клієнтів.

### 9. Фонові потоки й shutdown не керуються разом

Місця: `ui/app.py:637`, `ui/app.py:855`, `ui/app.py:1245`, `ui/app.py:2655`, `automation/runner.py:61`.

Окремі daemon threads не зареєстровані в диспетчері. `_on_close` скасовує сценарії й закриває UI без завершеного узгодження всіх фонoвих дій. `shutdown(wait=False)` не примушує активні workers завершитися. Водночас вони можуть ще потребувати UI-відповіді.

Виправлення: облік усіх робіт, припинення нових запусків, сигнал shutdown, закриття запитів взаємодії, обмежене очікування worker, фінальний запис результатів. Серверний runtime не повинен залежати від існування App.

### 10. Спільний AdsPower-клієнт і ліміти

Місце: `clients/adspower.py:38`.

Один клієнт містить спільні Session, api_key і змінюваний base_url. Загального регулятора частоти немає: кожний запит реагує на rate limit самостійно. Це ризик конкурентного доступу та хвиль повторів; пошкодження HTTP-сесії не відтворювалося і не заявляється як доведений дефект.

Виправлення: незмінна конфігурація клієнта на AdsPower-контекст, визначений власник HTTP-сесії або окремі сесії, загальний rate limiter і класифікація безпечних повторів. Не використовувати один глобальний API key для різних клієнтських контекстів.

## Перевірки цього аудиту

1. Запущено всі 9 `ControlTests` із `tests/test_operation_reliability.py` — успішно. Монітор ресурсів замінено mock, браузерні тести не запускалися.
2. Підтверджено caller-thread cleanup у screenshot cancel на fake driver.
3. Підтверджено втрату маркера через застарілий запис на тимчасовій SQLite-БД.
4. Підтверджено завислий облік runner після винятку fake scenario.

Важлива прогалина тестів: `test_cancel_never_calls_browser_on_ui_thread` перевіряє BaseScenario, але не перевизначений cancel скриншотів. Тому успішний тест не доводить єдину поведінку всіх сценаріїв. Робоча БД, профілі, документи й реальні заявки для цих перевірок не використовувалися.

## Рекомендована черговість підготовки

1. Уніфікувати cancel/pause/cleanup, виправити manual-assist очікування та гарантовану фіналізацію runner.
2. Ввести диспетчер операцій і резервування реальних профілів для всіх шляхів запуску.
3. Зробити атомарні переходи задач, прямий пошук за ID, незмінні дані запуску та надійний журнал зовнішніх дій.
4. Винести запуск РК і взаємодію з людиною з App у сервіси. Desktop перевести на ті самі сервіси.
5. Додати власників даних, tenant-контекст, окремі поштові/AdsPower-конфігурації та серверний runtime.
6. Підключити Telegram до підготовлених сервісів і випробувати два ізольовані клієнтські контексти.

Критерії регресії: зупинка A не впливає на B; один профіль не отримує двох власників; дві CAPTCHA мають різні запити; усі queued/running отримують коректний стан після shutdown; прогрес не стирає результат/маркер Submit; unknown не викликає повторної подачі; чужі account/task/document IDs недоступні.

Ці виправлення не вимагають повного переписування браузерного сценарію. Рішення про політику черги, довгі ручні паузи, збереження браузера після Stop та спосіб ізоляції серверних сесій слід погодити перед зміною поведінки продукту.
